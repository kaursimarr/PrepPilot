11. EXTRACTION SCRIPT
---------------------
The extraction script uses PyMuPDF.

Basic process:

1. Open the PDF.
2. Determine the number of pages.
3. Iterate through every page.
4. Extract text from the page.
5. Add a page marker.
6. Write the combined text into a raw .txt file.

Conceptually:

import fitz

doc = fitz.open(pdf_path)

for page_number in range(len(doc)):
    page = doc[page_number]
    text = page.get_text()
    output.write(text)

Why page markers matter:
RAG systems should ideally be able to identify where retrieved information came from. Page metadata can later be displayed with an answer or used for traceability.


12. TEXT CLEANING
-----------------
After extraction, raw PDF text may contain:
- repeated page headers
- page numbers
- excessive whitespace
- PDF formatting artifacts
- broken words
- unwanted front matter
- running headers
- table-of-contents content
- index material
- copyright/usage boilerplate

A cleaning stage was therefore introduced.

Typical operations:
- normalize whitespace
- remove unwanted boilerplate
- normalize repeated formatting
- preserve useful page information when possible
- remove obvious PDF extraction noise

Important lesson:
Removing ALL page markers too early makes page-aware chunking and source tracking harder.

Therefore, page information should ideally be retained until chunk metadata has been generated.

14. INITIAL CHUNKING APPROACH
-----------------------------
The first chunking approach used fixed-size chunks.

Example:
- target approximately 800 words
- overlap approximately 100 words

Each chunk was stored in JSONL.

Why fixed-size chunking was useful:
- simple
- predictable
- easy to implement
- useful for an initial RAG prototype

Problem:
Textbooks are structured documents. Fixed word counts can split:
- definitions
- examples
- algorithms
- explanations
- subsections
- code blocks

in the middle.

Therefore, semantic/structure-aware chunking was developed.


15. SEMANTIC CHUNKING
---------------------
The later chunking approach tries to respect textbook structure.

Desired metadata:

chunk_id
book_id
chapter
section
subsection
page_start
page_end
text

The chunker tries to detect:
- chapters
- sections
- subsections
- meaningful text blocks
- code examples
- page boundaries

Target chunk size:
approximately 800–1000 words depending on the document structure.

Maximum desired chunk size:
1200 words.

Chunks should not become excessively small unless the source structure requires it.


16. SEMANTIC CHUNKER DEVELOPMENT
--------------------------------
Several versions of the semantic chunker were tested.

The development process involved repeatedly checking:
- chunk sizes
- chunk boundaries
- chapter metadata
- section metadata
- page metadata
- front matter
- table of contents
- running headers
- index material
- PDF artifacts
- incomplete chunks
- duplicate IDs
- oversized chunks

One important issue discovered:
A PDF can contain repeated running headers such as chapter titles and page information. These can accidentally become part of the extracted text and pollute RAG retrieval.

Another issue:
Some PDFs contain front matter, tables of contents, references, appendices, character tables, or indexes that should not be treated as normal instructional material.

18. IMPORTANT CHUNK QUALITY LESSON
-----------------------------------
A chunk can pass numerical validation and still be semantically bad.

For example:
- a chunk can have 800 words but start in the middle of a sentence
- a chunk can contain unrelated topics
- a running header can contaminate the text
- an index can be mistaken for instructional material
- a table of contents can be treated as learning content

Therefore, both automated validation AND manual semantic review are required.

A review script was also included in the project scripts to inspect chunk quality.

21. WHY VECTOR DATABASE IS NEEDED
---------------------------------
When a student asks something like:

"Explain deadlock prevention."

the system should not ask the LLM to answer only from its general knowledge.

Instead:
1. Convert the query into an embedding.
2. Search the vector database.
3. Retrieve relevant textbook chunks.
4. Give those chunks to the LLM.
5. Generate a grounded answer.

This is Retrieval-Augmented Generation (RAG).

Benefits:
- answers grounded in uploaded material
- better syllabus alignment
- less hallucination
- source traceability
- personalized retrieval later
- connection between learning content and PYQs

"We designed PrepPilot as an AI-driven adaptive learning and examination system. We first selected structured learning resources for C, C++, Data Structures and Algorithms. 45. KEY TERMS TO KNOW FOR VIVA
-------------------------------
PDF Extraction:
Converting PDF content into machine-readable text.

Cleaning:
Removing extraction noise and unnecessary formatting.

Chunking:
Splitting large documents into smaller retrievable units.

Semantic Chunking:
Creating chunks according to document meaning/structure instead of only fixed word counts.

Embedding:
Converting text into numerical vectors representing semantic meaning.

Vector Database:
Stores embeddings and allows similarity-based retrieval.

RAG:
Retrieval-Augmented Generation. Relevant source chunks are retrieved first and supplied to the LLM as context.

LLM:
Large Language Model used for language understanding and generation.

Student Knowledge Model:
Representation of the student's estimated mastery of different topics.

Adaptive Learning:
Changing the learning content/questions based on the student's current knowledge and performance.

Knowledge Acquisition:
Pipeline for converting raw educational resources into structured machine-usable knowledge.
